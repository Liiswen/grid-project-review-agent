# 电网数字化项目材料审查平台

这是一个本地 Web 审查工具：上传项目资料 ZIP，选择审查阶段，系统从资料包中定位证据、调用豆包逐条审查，并导出 Excel 问题清单。适用于电网数字化开发实施项目的材料完整性和合规性初审。

## 1. 启动

以下命令在本目录（`agent`）执行。建议使用 Python 3.12，并为本项目单独创建虚拟环境。

```powershell
# Windows PowerShell
python --version  # 应显示 Python 3.12.x
python -m venv .venv
.\.venv\Scripts\Activate.ps1
python -m pip install --upgrade pip
python -m pip install -r requirements.txt
python app.py
```

若版本不是 Python 3.12，请先安装 Python 3.12，并确保终端中的 `python` 指向该版本后再执行以上命令。

启动成功后，在浏览器打开：[http://127.0.0.1:5000](http://127.0.0.1:5000)

## 2. 配置 API Key（两种方式）

系统使用豆包 API。可选择以下任一方式提供 API Key：

1. **网页输入**：在“火山引擎·豆包 API Key”输入框中填写 Key 后发起审查，适合临时使用。
2. **本地配置文件**：在本目录创建仅供本机使用且不提交到版本库的 `local_settings.py`：

```python
VOLC_API_KEY = "你的_API_Key"
```

本地配置适合个人开发环境。网页输入框留空时，服务端会使用本地配置的 Key；本地 Key 不会回填到浏览器页面。不要将真实 API Key 写入 README、检查要点、截图、导出报告或提交到代码仓库。

## 3. 怎么审查一个项目

1. 在网页上传项目 ZIP。
2. 选择要审查的阶段，例如“项目采购”。
3. 等待系统完成解析、证据检索和逐条审查。
4. 下载 Excel，重点复核“无法判断”和“不合格”项。
5. 点击人工复核中的文件链接，查看原件页面和模型引用的证据位置。

上传 ZIP 可以包含内嵌 ZIP。系统会有限度地递归展开其中的项目文件。

## 4. 先理解结果：四种结论


| 结论   | 含义                            |
| ---- | ----------------------------- |
| 合格   | 已定位到足够证据，且与检查要点一致。            |
| 不合格  | 已读取的证据明确显示不符合要求。              |
| 无法判断 | 已定位部分材料，但缺少必要字段、页面、系统留痕或交叉证据。 |
| 不适用  | 检查项的前提条件未发生，例如确认未发生分包时的分包链材料。 |


“无法判断”不等于“未上传”。结论应说明已查到什么、还缺什么，并给出可执行的人工核验动作。

## 5. 系统如何读取长文件

系统不会将整个 ZIP 或所有图片直接发给大模型，而是使用证据管线：

```text
ZIP / 内嵌 ZIP
  → 文件路径与类型索引
  → 按检查要点定位候选文件
  → 多格式全文解析
  → 路径 + 页码/区块 + 正文 的证据索引
  → 按检查项召回相关证据
  → 豆包审查并引用证据位置
```

不同格式的处理方式：


| 文件类型      | 处理方式                                    |
| --------- | --------------------------------------- |
| 文字 PDF    | 按页提取正文。                                 |
| 扫描 PDF    | 全页 OCR 形成可检索页级文本；图片用于复核红章、签名、手写日期和复杂表格。 |
| DOC / RTF | 提取正文和表格文字；RTF 格式的 `.doc` 可直接读取。         |
| DOCX      | 提取段落文本。                                 |
| WPS       | 读取 Word 二进制正文流。                         |
| XLSX      | 提取工作表和有效单元格。                            |


因此，模型收到的不是“所有文件的全部图片”。扫描件会保留全页 OCR 文本；仅与当前检查项相关的关键页面图片会发送给模型。人工复核页面可按需打开 PDF 的任意页。

## 6. 检查要点在哪里

当前实际生效的规则在 `检查要点/`，按项目阶段划分：

```text
项目前期.txt
项目采购.txt
项目建设.txt
上下线.txt
项目验收.txt
决算.txt
转资.txt
```

每条检查项必须保留以下字段：

```text
【检查项1】检查内容
【Excel序号】1
【项目环节】项目采购
【对应文件】文件类型
【依据】制度或检查表来源
【相关要求】取证方法、交叉关系、合格/不合格/无法判断边界
【备注】适用条件或特殊说明
【建议检索路径】归档目录提示
【来源定位】检查表行号或来源位置
```

`【建议检索路径】`用于帮助定位文件，不是新增审查要求。证据链、查找方式和条件适用边界应写在同一检查项的`【相关要求】`中。

## 7. 修改检查要点后的必做事项

1. 保持字段名和顺序不变；一条检查项的字段尽量各占一行。
2. 日期、金额、主体名称等交叉核验，应在`【相关要求】`明确文件来源和比较口径。
3. 条件材料必须写明适用前提。例如，未确认发生分包时，不得直接要求分包合同。
4. 签章、红章、手写日期和扫描表格必须要求查看页面图片，不能只依赖文本。
5. 修改后执行解析检查：

```powershell
python -c "from preliminary_rules import load_rule_checkpoints; print(len(load_rule_checkpoints(r'检查要点\\项目采购.txt', '项目采购')))"
python -m py_compile *.py
```

1. 重启 Web 服务后再审查。已运行的 Flask 进程不会自动加载修改后的 Python 文件或检查要点。



## 8. 常见问题



### 上传 ZIP 报错

先检查 ZIP 是否损坏、是否超过上传限制、磁盘是否有足够空间，以及内嵌 ZIP 是否异常。不要删除历史上传文件来“试试”，应先确认没有正在执行的任务和文件保留需求。

### 审查很慢

首次处理长扫描 PDF 时，系统需要逐页 OCR 并建立证据索引，耗时会明显高于文字 PDF。这是为了避免“文件已上传但模型未读到”的误判。

### 结果仍称“未提供”

先检查结果中列出的候选文件路径和证据引用。若文件实际存在但未进入候选集，应优先完善该检查项的`【建议检索路径】`和`【相关要求】`，而不是只增加一句泛化提示词。

### 修改后没有生效

通常是旧服务仍在运行。停止当前服务后，重新激活 `.venv` 并执行：

```powershell
python app.py
```



## 9. 重要配置

常用运行参数在 `config.py`：

```text
MAX_UPLOAD_BYTES                # 单个 ZIP 上传上限
MAX_NESTED_ARCHIVE_DEPTH        # 内嵌 ZIP 最大展开层数
MAX_CANDIDATES_PER_CHECKPOINT   # 单检查项候选文件数
REVIEW_CONCURRENCY              # 并发审查数
ENABLE_FULL_SCAN_OCR            # 是否启用扫描 PDF 全页 OCR
OCR_RENDER_DPI                  # OCR 渲染精度
MAX_OCR_PAGES_PER_FILE          # 单文件 OCR 页数上限
```

长扫描件的准确性与处理时间需要平衡。若项目资料普遍超过 OCR 页数上限，应在提高上限前评估机器性能、磁盘空间和任务处理时长。

## 11. 如何修改“检查要点”

`检查要点/`是平台唯一的运行规则来源。

### 修改前先判断能否修改

1. 先找到对应阶段和原始检查项，确认修改不会改变检查表本身的要求。
2. 只保留有明确制度依据、能落到具体材料或字段的内容。
3. 需要新增硬性检查项时，必须有明确制度或检查表依据，并在`【依据】`和`【来源定位】`中说明来源；不能仅凭推测新增。

### 修改方式

直接编辑对应阶段的 TXT，例如：

```text
检查要点/项目采购.txt
```

每条检查项必须保留既有字段名、字段顺序和一行一个字段的格式：

```text
【检查项1】检查内容
【Excel序号】1
【项目环节】项目采购
【对应文件】文件类型
【依据】制度或检查表来源
【相关要求】取证方法、交叉关系、合格/不合格/无法判断边界
【备注】适用条件或特殊说明
【建议检索路径】归档目录提示
【来源定位】检查表行号或来源位置
```

### 编写`【相关要求】`的标准

每一条应写清以下内容，而不是只写“核验是否合规”：

1. 到哪些标准目录、内嵌 ZIP 或文件类型中检索；路径是通用归档路径，不能写某个项目的文件名、金额、日期或单位名称。
2. 需要读取的字段，例如项目名称、金额口径、签发日期、合同主体、签字盖章、附件名称或分包类型。
3. 需要交叉核验的材料及关系，例如“批复金额—中标通知书—全部拆分合同”“计划下达—采购公告—中标通知书”。
4. 合格、不合格和无法判断的边界。只有已读证据明确相反时才可判不合格；材料已定位但字段未读到、OCR/图片无法辨认或缺少系统留痕时，应判无法判断。
5. 条件适用前提。例如已确认发生分包时才核验分包申请、审批、合同、资质和考核链；不得在未确认分包事实时直接判缺分包材料。

### 特别注意

- 不得把“候选文件未命中”写成“项目未提供”；先检查建议检索路径、内嵌 ZIP 和文件实际解析状态。
- WPS、DOC 等文件已定位但正文未能读取时，应写“已定位，正文待人工核验”，不能写“未提供”。
- 扫描件中的红章、签名、手写日期和复杂表格应要求查看原始页面图片；OCR 文字只能辅助定位。
- 金额比较必须说明同一项目、同一含税/不含税口径及计算关系，不能混用批复金额、中标金额和合同分项金额。
- 日期比较必须写明每一个日期的来源；只缺其中一条时间链的材料时，只对该子项判无法判断。
- 不得把某次审查发现的具体项目事实、文件名、金额、日期或供应商名称固化到通用规则中。

### 修改后的验证步骤

在 `agent` 目录执行：

```powershell
python -c "from preliminary_rules import load_rule_checkpoints; print(len(load_rule_checkpoints(r'检查要点\\项目采购.txt', '项目采购')))"
python -m py_compile *.py
```

随后重启 Web 服务，并用至少一个真实项目 ZIP 回放。重点确认：候选文件路径是否正确、内嵌 ZIP 是否被展开、关键证据是否被引用到、条件项没有被机械判缺失。
